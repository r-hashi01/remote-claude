# 0006. リトライは runner 起動前に限る

- Status: Accepted
- Date: 2026-08-08

## Context

`Sandbox operation ... was interrupted while the platform was updating the
sandbox runtime` によるジョブ失敗を、通常利用の中で**2回**観測した。
Cloudflare 側でサンドボックスランタイムが更新され、実行中の操作が中断される。
こちらのバグではなく、運用上の常態と見るべき事象。

放置するとジョブが不定期に失敗し、開発基盤として信用できない。

## Decision

一過性のプラットフォームエラーは自動リトライする。ただし
**runner が起動する前に失敗した場合に限る**（最大3回）。

この境界には理由がある。

| 失敗した時点 | 副作用 | リトライ |
|---|---|---|
| sandbox 作成 / clone / job.json 書き込み | **なし** | ✅ 安全 |
| runner 起動後 | **ユーザーのプロンプトが実行済みかもしれない** | ❌ しない |

runner 起動後の再試行は「同じ処理をやり直す」ではなく
「**プロンプトをもう一度実行する**」であり、意味が違う。コミットが二重に生まれたり、
外部への副作用が二重に走る可能性がある。

判別はメッセージパターンで行う。網羅的ではないが、誤って
「壊れているジョブ」をリトライし続けるより、取りこぼして人間に見せるほうが安全。

## Alternatives

**全面リトライ。** 実装は単純だが、プロンプトの二重実行を招く。冪等性の保証が無い以上、選べない。

**リトライしない。** 観測2回という頻度では、基盤として使い物にならない。

**runner 側にチェックポイントを持たせて途中再開する。** 正しい方向ではあるが、
いま必要な複雑さではない。頻度が上がったら再検討する。

## Consequences

- 起動時の一過性障害でジョブが落ちなくなる
- リトライは `attempts` に記録され、ログにも残る。黙って再試行しない
- runner 起動後の一過性障害は**依然としてジョブを失敗させる**。これは意図した挙動で、
  二重実行を避けるための代償
- 判別パターンは観測に基づくため、新しい文言が出たら追加が要る

## Addendum — 2026-08-12: コンテナが消えた場合は起動後でもリトライする

この ADR の境界（runner 起動後はリトライしない）には穴があった。
根拠は「起動後の再試行はプロンプトの二重実行になる」だが、
**コンテナ自体が消えた場合、実行された結果は何も残っていない** —
workspace も checkout も agent の成果も、コンテナと一緒に消える。
二重実行になるものが存在しないのだから、この場合の再試行は
「やり直す」のほうであり、この ADR が禁じた「もう一度実行する」ではない。

実際に2つの形で観測した。

| 観測 | 症状 | 検知 |
|---|---|---|
| deploy 完了の12秒後に開始 | コンテナのロールアウトが実行中のインスタンスを drain | `was interrupted while the runtime connection was closing` |
| 開始から約2分（3回連続） | `SANDBOX_SLEEP_AFTER: "2m"` が agent 実行中にコンテナをスリープさせた | **エラーは何も出ない** |

後者が厄介だった。sandbox は id で参照するため、実体が無ければ
**空の新インスタンスが黙って作られる**。exec は成功し、例外も出ず、
ただ executor 自身が書いたファイルが存在しない。
だから判定は「プラットフォームのエラー文言」ではなく
**executor が書いた `runner.mjs` が消えているか**で行う。
runner には作れない状態であり、置き換えが残す唯一の痕跡である。

`pushing` 以降は対象外とする。sandbox の外に痕跡を残す最初の段階であり、
そこから先の再試行は無料ではない。

なお `SANDBOX_SLEEP_AFTER` を短く保つ判断は、
「sandbox はジョブ毎で再利用しないから、この窓はジョブ終了〜teardown の間だけ」
という理屈で正当化されていた。再利用については正しく、
**タイマーが何を計っているかについては黙っていた** — 計っているのは
コンテナへのリクエストの無活動であり、中で走るプロセスは数えない。
旧方式（パイプラインを長寿命の `exec` で回す）では副作用としてコンテナが
掴まれていたため、この値は無害に見えていた。
ADR 0004 で pipeline をコンテナ内に移し、
その後 runner を `startProcess` に替えた時点で、掴む主体が居なくなった。

コメントはこれに気付けない。`src/conventions.test.ts` に
**sleep タイマーがジョブ予算より長いこと**を検査するガードを置いた。

## Addendum — 2026-08-18: 推測をやめ、プラットフォームに聞く

この ADR は判別を**メッセージのパターン**で行うと決めた。当時はそれしか無かった。
そしてこのファイル自身が代償を記録している —
「二番目の文言は実際のジョブを1件失った。パターンが片方の言い回しを知っていて
他方を知らなかったせいだ」。

SDK は最初から構造化して投げていた。`OperationInterruptedError` /
`ContainerUnavailableError` / `RPCTransportError` が持っているもの:

| フィールド | 意味 |
|---|---|
| `reason` | `runtime_replaced` / `transport_disposed` / `sandbox_lifetime_changed` / `recovery_exhausted` など |
| `retryable` | **再試行して安全かの答え** |
| `phase` | どの段で中断を検知したか |
| `operation` | `command.execute` / `backup.restore` など |
| `admitted` | **副作用がコンテナに到達したか**（`true` / `false` / `'unknown'`） |

**参照は1箇所も無かった。** 判断は正規表現で、記録に残るのはメッセージだけ。
コンテナ起動の失敗を1日かけて調べても原因が特定できなかったのはそのためで、
`reason` の1語があれば「デプロイで差し替わった」のか
「サンドボックスが破棄された」のかが即座に分かった。

**決定を2つ変える。**

1. **記録する。** `reason` / `phase` / `operation` / `retryable` / `admitted` を
   ログとジョブの `error` に残す。読む人が最初に聞くのはこれである
2. **`retryable` で判断する。** 正規表現は**構造が無いときの後退経路**に降格した。
   DO の境界を越えたエラーは name と message だけを持って到達するので、
   後退経路は消せない

`admitted` はこの ADR の中心にある問いへの答えである。ここは
「runner 起動後の再試行はプロンプトの二重実行になる」という理由で境界を引いたが、
**到達したかどうかは推測するしかなかった**。いまはプラットフォームが答える。
`admitted: true` なら再試行しない — それは再試行ではなく2回目の実行だから。

層は守っている。SDK を知るのは `infrastructure/sandbox/failure.ts` だけで、
そこが `PlatformFailureDetails` に翻訳する。domain の規則はその形だけを見るので、
workerd 無しでテストできる。
