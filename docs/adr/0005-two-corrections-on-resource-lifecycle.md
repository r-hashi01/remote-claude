# 0005. リソースライフサイクルに関する2つの判断の訂正

- Status: Accepted
- Date: 2026-08-08

## Context

孤児 Sandbox の扱いについて、**2回続けて判断を誤った**。ADR として残すのは、
結論より誤り方のほうが再発防止に効くため。

### 誤り1: 観測の読み違い

`wrangler containers list` の `LIVE INSTANCES 3` を「孤児が同時実行枠を埋めている」と読み、
「キューが詰まる」と断定して P0 に置いた。

**反証は既に手元にあった。** その表示のままジョブが正常に completed している。
本当に枠が埋まっていれば待たされたはずだった。値が `max_instances` と完全一致し、
失敗4件・成功1件・複数回の deploy・40分のアイドルを通じて一度も動かない不自然さにも
引っかかるべきだった。

実際には provisioned capacity であって稼働数ではない。

### 誤り2: 判断基準の誤り

訂正後、公式ドキュメントで scale-to-zero（アイドル中は課金されない）を確認し、
「課金されていないから急がない」として P1 へ降格した。これも誤り。

- **「課金されない」結論自体が未検証の前提に乗っていた。** スリープが常に起きることを
  確認していない
- **「測れないから降格」は逆。** 基盤にとって「確保した資源を回収できているか分からない」
  ことは、それ自体が欠陥

## Decision

1. 孤児回収は残す。理由を「コスト」から**「基盤は確保した資源を確実に回収できなければ
   ならない」**に置き換える
2. Sandbox の**割り当て台帳**を持つ。外部の指標に頼らず、自分で説明できるようにする
3. 台帳を巡回の駆動源にする。ジョブ表の走査をやめる

破棄の失敗は握り潰さず、試行回数と最終エラーを記録する。繰り返し消えない Sandbox こそ
台帳が存在する理由であるため。

## Alternatives

**外部メトリクスを探し続ける。** `wrangler containers list` が答えでないと分かった時点で、
他の外部指標も同じ疑いがかかる。Sandbox を作っているのは JobManager なので、
記録する主体もそこであるべきだった。

## Consequences

- `GET /sandboxes` / `remote-claude sandboxes` で説明できる。CLI はジョブが動いていないのに
  outstanding が残っていれば exit 1 を返すので、報告ではなく検査として使える
- 検証できた。1ジョブで 0/0 → outstanding 1（実行中）→ 0 outstanding / 1 reclaimed
- 教訓として残すもの: **手元の観測と矛盾する主張をしていないか先に確認する**、
  **「測れない」は優先度を下げる理由ではなく上げる理由**
