# 0016. レジストリに毎回聞かない

- Status: Accepted
- Date: 2026-08-17

## Context

`install` が `ECONNRESET` / `ETIMEDOUT` で落ちる失敗が続いた。5回すべて大きな転送の最中で、
長い無出力区間の直後。小さいパッケージでは落ちない。npm は既定で fetch を2回再試行するので、
**再試行を生き延びた失敗**だった。そして成功時は 56s / 78s / 111s ——
ランダムなパケットロスではなく、**スループットの崖**である。

まず転送の形を変えた（並列 15 → 8 → 3 → 1、ADR なしの実装変更）。実測はこうなった。

| 指標 | 値 |
|---|---|
| fetch 件数 | 137 |
| 所要時間の中央値 | **1980 ms** |
| 最大 | **27609 ms**（1パッケージ） |
| install 合計 | 44.6 秒（従来の成功は 56〜111 秒） |

健全なレジストリ取得は通常 500ms 未満である。**経路そのものが遅い。**
形を変えたことで崖からは距離が取れたが、137 件を毎回取り直す構造は残っている。

## Decision

**リポジトリごとに npm のキャッシュを R2 に持ち越す。**

- 置き場所は `/workspace/.npm-cache`。workspace の snapshot 機構（ADR 0011）が
  届くディレクトリであり、workspace 自身の snapshot からは**除外**する
  （継続が木の中にキャッシュの複製を運ばないため）
- 鍵は**リポジトリ**。lockfile のハッシュではない。npm のキャッシュは内容アドレス方式で
  加算的なので、依存が動く前のキャッシュでも**動かなかったもの全部**に答える。
  lockfile 鍵は、コンテナから lockfile を読む往復を増やした上で、
  依存が1つ動くたびに空から始めることになる —— 避けたいコストを、
  誰も得しない厳密さのために払う形になる
- **復元は runner 起動前。** install が最初にネットワークへ出る段だから
- **保存は終端の記録の後。** workspace とは違う。workspace は
  「継続できる」という呼び出し側への約束なので記録より前に置いた（ADR 0012 の議論）。
  キャッシュは**まだ存在しないジョブのための最適化**で、誰も待っていない
- **ネットワークに出たときだけ保存する。** 復元したキャッシュで全部済んだ install は
  何も足していない。同一の複製で置き換えるのは、出発点に着くために転送を払うこと

## Alternatives

**コンテナ image にキャッシュを焼く。** deployment 既定のリポジトリだけ速くなる。
`--repo` の任意リポジトリには効かず、private repo は build 時に credential を要する。

**node_modules を持ち越す。** キャッシュより大きく、lockfile とプラットフォームに固く縛られる。
npm のキャッシュは層として正しい位置にあり、そこからのリンクは秒で終わる。

**何もしない（形の変更だけで様子を見る）。** 崖から距離は取れたが、
遅い日には再び届く。137 件という数は変わっていない。

## Consequences

- 2回目以降の install は、変わっていない依存についてはネットワークに出ない
- キャッシュを持たない deployment は今までどおり動く。**フラグは無い** ——
  置き場所があることが決定である（`BACKUP_BUCKET` と同じ形）
- キャッシュは1リポジトリ1行で、置き換わる。世代を残さない ——
  現在であることだけが価値のものの履歴を貯めることになる
- `loglevel=http` を入れてあるので、次に崖が出たときは
  **どのリクエストで止まったか**がログに残る
